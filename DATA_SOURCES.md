The coverage examples reuse the Southwark outline from `../london/boroughs_subset.geojson` (OGL, above) and
`../london/synthetic_demand.csv`. That file's `population` field is used as *synthetic demand units*,
not observed charging or toilet demand.

Caveats:

* **Coordinates:** 18 of the 163 records are OSM ways whose coordinate is the centre of their bounding box,
  not an entrance.
* **Location:** 84 of the records lie inside the Southwark polygon. The rest lie inside its bounding box, and
  the examples keep them as existing facilities.
* **Accuracy:** tags are as mapped by contributors. Current existence, availability, opening hours, fees,
  indoor location and wheelchair access are not verified.
* **Toilet access:** the toilet example treats `access=yes`/`permissive` as eligible (28). It excludes
  `customers`/`permit`/`private` (18). The 54 records with no `access` tag are excluded unless the user opts
  in.
* **Charger access:** the charging example by default uses all 63 records as tagged. Their access tags are
  5 `yes`, 2 `no`, 1 `customers`, 1 `taxi` and 54 missing. An optional conservative filter keeps only the
  5 `yes`/`permissive` records; the raw file is unchanged either way. The example does not assert public
  availability.

## Provenance and limits

* Both real files were obtained on **2026-09-27**; their SHA-256 values are in `manifest.json`
  (`boroughs`: `126dd549…ac0c`, `chargers`: `0ba090eb…80b1`).
* The charger layer is **historic** (the publisher marks it as not recently updated). It is used only to
  exercise file handling, CRS conversion and the three modules. It says nothing about which chargers exist
  or work today, and no live availability is implied.
* The borough label attached to each charger is the publisher's own attribute. GeoVerify compares it with
  the publisher's borough polygons; this is a consistency check between two open files of possibly
  different dates and boundary versions, not independent ground truth.
* Only a central-London subset is bundled. Chargers whose coordinate lies in a non-bundled borough but whose
  label names a bundled one (or vice versa) are reported by GeoVerify as `OUTSIDE_ALL_SUPPLIED_ZONES`
  rather than silently dropped.
* Synthetic files are demonstrations of method. Their numbers (probe results, matches, population coverage)
  are properties of the generator, not observations of London. That they are generated does not alter the
  licence obligations of the OGL or CC BY material they were derived from.

## Reproducing the bundled data

```bash
# Offline, nothing else needed: regenerate the synthetic files from the bundled real subsets.
# Refuses to run if the bundled real subsets no longer match manifest.json.
python scripts/prepare_data.py --synthetic-only

# Rebuild everything from official files you already hold (state when you obtained them):
python scripts/prepare_data.py --boroughs london_boroughs.geojson --chargers Rapid_charging_points.gpkg \
    --retrieved-at 2026-09-27

# Optional, needs network: fetch the current official files; the manifest records today's UTC date.
python scripts/prepare_data.py --download raw
```

The bundled sample corresponds to files obtained on 2026-09-27 (hashes in `manifest.json`). Publisher files
are mutable: a fresh `--download` may produce different subsets or counts, so use `--out` to write them
elsewhere instead of replacing the pinned sample. `--retrieved-at` is mandatory when you supply your own
files, so a manifest never carries a date that was not stated. The script expects the borough GeoJSON in
EPSG:4326 with `name` and `gss_code` fields and the charger GeoPackage table `Rapid_charging_points`
(columns `fid, borough, easting, northing, latitude, longtitude, sitename, siteid`; the source spelling
`longtitude` is kept). Output is deterministic: identical inputs give byte-identical files, and the manifest
hashes only the five generated data files. The download URLs are not exercised by the automated tests, which
run offline.
